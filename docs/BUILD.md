# Reproducing the WASM core build

Run all commands below from the repository root (`swbf2-web/`).

## One-time setup

```sh
git clone https://github.com/OpenSWBF2/OpenSWBF2 vendor/openswbf2
git clone https://github.com/emscripten-core/emsdk vendor/emsdk
vendor/emsdk/emsdk install latest && vendor/emsdk/emsdk activate latest
```

### Bring-Your-Own-Copy GameData

No copyrighted game files are included in this repository. To play in the browser, simply open `/play` and select your own legal **Star Wars Battlefront II (2005)** `GameData` folder (Steam, GOG, or retail Disc) directly in the browser.

For running the automated local test suite or private LAN self-hosting (`--serve-gamedata`), place or symlink your own copy's `GameData/data/_lvl_pc` at `data/Star wars battlefront 2/GameData/data/_lvl_pc` (or pass `--gamedata-dir /path/to/_lvl_pc`) and run `python3 tools/gen_manifest.py`. `tools/lvl_reader.py` and `tools/lvl_survey.py` parse the `ucfb` chunk containers; see `docs/data-format.md`.

## Build

```sh
python3 tools/prepare_tree.py     # vendor/openswbf2/src -> build/src_fixed (documented edits)
python3 tools/include_pass.py 2   # additive (8-way parallel): insert #include for incomplete types
python3 tools/shim_autogen.py 2   # converge platform vocabulary into spike/shim/generated_types.h
./tools/compile_core.sh           # compile all 771 core TUs (incl. pcRedRenderer.cpp) -> build/core.a
```

Or run all four stages in order with `./tools/build_core.sh`. For the Phase 0 WebGPU smoke test
(`emdawnwebgpu`, Dedicated Worker + `OffscreenCanvas`), run `./tools/build_webgpu_smoke.sh` and
`vendor/emsdk/node/24.19.0_64bit/bin/node browser/webgpu_smoke_check.mjs`. For the Phase 1 OPFS
streaming VFS verification, run `vendor/emsdk/node/24.19.0_64bit/bin/node browser/vfs_check.mjs`.
For the Phase 2/3 real engine `RedRenderer`/`FLRenderer` WebGPU renderer and SM 1.1 → WGSL shader
validation check (`tat/tat2` + `2,332 vs_1_1` + `226 ps_1_1` shaders + `RedFont` HUD), run
`./tools/build_browser.sh` and `vendor/emsdk/node/24.19.0_64bit/bin/node browser/webgpu_render_check.mjs`
(and `python3 tools/audit_sm1_shaders.py` to audit `core.lvl` shaders). For the Phase 4 native `GameState` (`ShellState` <-> `MissionState`), DirectInput8 profile login +
OPFS `.profile` persistence, live `.mvs` Bink1 playback, and live Instant Action gameplay spawn

`vendor/emsdk/node/24.19.0_64bit/bin/node browser/phase4_gamestate_check.mjs`. For the Phase 5 interactive DOM -> `SharedArrayBuffer` input (keyboard/mouse/PointerLock/gamepad)
and real 3D `SoundFL` -> `SharedArrayBuffer` 48 kHz WebAudio AudioWorklet check, run

`tools/measure.sh` is the compile-rate measurement; per-file results are in `build/results.tsv`
(module, ok/error, first error text). To see the first errors of every failing file with the file
path attached, run the snippet in `docs/shim-layer-results.md`'s style: compile each failing file
individually and print the first two `error:` lines.

Link check (undefined symbols allowed, just to prove the objects are usable and to measure the gap):

```sh
export PATH="$PWD/vendor/emsdk:$PWD/vendor/emsdk/upstream/emscripten:$PWD/vendor/emsdk/node/24.19.0_64bit/bin:$PATH"
emcc build/core.a browser/main_stub.cpp -O0 -sSTANDALONE_WASM -sERROR_ON_UNDEFINED_SYMBOLS=0 \
     -sALLOW_MEMORY_GROWTH=1 -o build/core_smoke.wasm
```

The undefined-symbol work list is regenerated by `docs/backend-surface.md`'s method:
`llvm-nm -u --extern-only` over the archive, minus everything defined by the archive itself and by
emscripten's `sysroot/lib/*.a` and `libclang_rt*.a` (use `LC_ALL=C comm` - a locale-dependent sort
silently leaves already-defined symbols in the list, which cost a false "D3DX math is missing" scare).

## The native oracle

The native oracle (the same engine sources built for the host, used to check the browser build's
numbers against a native one) is a 32-bit build, and it needs the 32-bit C library:

```sh
sudo apt-get install libc6-dev-i386 g++-multilib
./tools/compile_native.sh          # -> build/native_core.a
./tools/build_native_oracle.sh    # -> build/native_oracle/ground_oracle
python3 tools/ground_oracle_check.py
```

It is 32-bit because the engine is: `GameState.cpp:1668` allocates four bytes per pointer in a
vector of pointers, and `RedMemory.cpp` truncates heap pointers to `unsigned int`, so a 64-bit
build corrupts its own heap. `docs/ground-oracle.md` has the measurement.

## Toolchain caveats learned the hard way

* **Pass the sysroot explicitly.** `clang` from `vendor/emsdk/upstream/bin` needs
  `--sysroot=vendor/emsdk/upstream/emscripten/cache/sysroot`; without it nothing finds `math.h`.
* **`-fms-extensions` is mandatory** (`__declspec`, `__cdecl`, anonymous struct/union members) and
  makes MSVC calling conventions a warning instead of an error on wasm32.
* **System `node` is broken here** (`webidl.util.markAsUncloneable`). Always use
  `vendor/emsdk/node/24.19.0_64bit/bin/node`.
* **Warnings are not errors.** Measure with `-Wno-narrowing` (FOURCC values in `case` labels) and
  `-Wno-address-of-temporary`; anything broader buries the ~49 real problems under 600 warnings.
* **Never force-include C++-only shim content into C files.** LuaFL and ZlibFL are C; when the prefix
  pulled in `d3dx9math.h` with constructors, all 9 ZlibFL files died. Every D3D/COM shim header is
  wrapped in `#ifdef __cplusplus`.
* **Disk is at 98% (≈10 GB free).** `build/obj` + `build/core.a` are ~180 MB; delete `build/obj`
  after archiving if space is tight, and do not extract a second copy of the game data.

## The browser module and the demo

```sh
./tools/build_browser.sh      # -> build/browser/swbf2.{js,wasm}
./tools/demo.sh [port]        # manifest + static server, bound to 0.0.0.0 (prints every address)
./tools/demo.sh 8123 127.0.0.1   # loopback only - otherwise any device on the LAN can open it
./tools/lan_serve.sh start    # durable LAN server: http 8123 + https 8443 + multiplayer 8133
./tools/lan_check.py          # prove this machine really serves the LAN (docs/lan-play.md)
./tools/measure_backends.sh   # whole-archive link: what the engine still demands (0 today)
```

`build_core.sh` is the whole core pipeline in order: `prepare_tree.py` → `include_pass.py` →
`shim_autogen.py` → `compile_core.sh`. It must be run as a whole — `prepare_tree.py` regenerates
`build/src_fixed` from scratch, so running it alone throws away the includes that
`include_pass.py` worked out and the compile rate collapses. Use `--skip-prepare` to recompile
against the current prepared tree.

Things that cost time to rediscover, each verified the hard way:

* **`llvm-ar` is not on the emsdk PATH.** Anything in a script that shells out to it must resolve
  `vendor/emsdk/upstream/bin/llvm-ar` itself, and under `set -e` a failed command substitution
  aborts the script *silently* — which once looked like a successful build with a stale module.
  Counters in build scripts need `|| true`.
* **The page must be rebuilt with the module.** The page's build numbers come from `-DSWBF2_ENGINE_OBJECTS`
  / `-DSWBF2_ENGINE_SCOPE`, derived from `build/core.a` and `build/results.tsv` at link time, so the
  status line cannot claim more than the binary carries.
* **`-lc++abi-noexcept` has to be named explicitly.** The decompiled objects are built
  `-fno-exceptions` but still reference `__cxa_guard_acquire` and sized `operator delete`; nothing in
  the link asks for exceptions, so Emscripten adds no C++ runtime and the symbols go unsatisfied.
* **`-sENVIRONMENT=web,node`**, so the same artifact serves the page, `browser/node_test.mjs` and
  `tools/audit_textures.mjs`.
* **`SUPPORT_LONGJMP=1` at both compile and link**, and only for `LuaFL/src/ldo.cpp` at compile:
  wasm32 Emscripten has no setjmp in libc, it lowers it, and the rest of the tree must not be
  affected by that lowering.
* **Do not export `malloc`/`free`.** Anything that needs to move pixel data across the wasm boundary
  should be a single C call that returns a value or fills `swbf2_last_report()`; out-parameters via
  raw pointers are how the first version of the host leaked and corrupted.
* **WebGL extensions are only enabled once something asks for them on that context.** The engine
  stays off the DOM, so `host.js` calls `getExtension('WEBGL_compressed_texture_s3tc')` on the
  shared canvas before the engine uploads the first DXT texture.
* **The engine's two views of a container must share one walk policy.** `kChunkWalkDepth` plus
  container-only descent (`IsContainerId`) is what makes `swbf2_probe_file`'s counts agree with the
  texture/script index lookups. Descending into arbitrary chunks reads a texture's pixel data as
  chunk headers and, on a 60 MB file, produces millions of plausible ones — the walk never
  finishes, which looked like a hang in the audit rather than a bug.
  The model path follows the same rule and states it: it descends only through the ids the engine's
  own reader defines as parents (`modl`→`segm`, `wrld`→`inst`→`INFO`), and nothing else. That is why
  instances inside a group id outside `IsContainerId` - `lvl_/@Sc*/wrld/inst` in tat2 - are not
  reached, and why the oracle counts those separately instead of blending them into a disagreement.
